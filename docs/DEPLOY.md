# Deploying

Production runs on [Render](https://render.com): one web service built from this repository's
`Dockerfile`, and one Render Postgres database, both described in `render.yaml`. Render deploys on
every push to the Blueprint's branch, once CI passes. Why Render and not Railway is recorded in
[Sprint 5's decisions](sprints/sprint-05.md#decisions-made-this-sprint).

## What happens on a deploy

1. A push reaches the Blueprint's branch. `autoDeployTrigger: checksPass` makes Render wait until
   GitHub Actions (lint, tests on SQLite and on Postgres, the CSS check) has passed.
2. Render builds the image from `Dockerfile`.
3. **Pre-deploy:** `alembic upgrade head` runs in the new image, against the production database.
   If it fails, the deploy stops there and the previous version keeps serving.
4. The new container starts (`fastapi run`, on the port Render assigns through `$PORT`).
5. Render calls `/api/health` until it answers 200, then moves traffic to the new version and
   stops the old one. A version that never becomes healthy never takes traffic.

Migrations run before the code that needs them, so a new version never runs against an old schema.
The old version keeps running for a few seconds after the migration, so a migration has to leave
the schema usable by the previous release. That rules out dropping or renaming a column in the
same release that stops using it. Do it in two deploys.

Render serves HTTPS, redirects plain HTTP to it, and compresses responses, so the app does neither.

## Environment variables

`render.yaml` sets these on the service. None of their values live in the repository.

| Variable | Value | Why |
| --- | --- | --- |
| `MAKARIOS_ENVIRONMENT` | `production` | Turns on the production checks: no debug, no API docs, no seeding. |
| `MAKARIOS_DATABASE_URL` | from the `makarios-db` database | The private connection URL. The app rewrites its `postgresql://` scheme to use psycopg 3. |
| `MAKARIOS_SECRET_KEY` | generated by Render | Signs the admin's session cookie. Anyone who has it can forge a login. |
| `MAKARIOS_PROXY_HOPS` | `1` by default; add it to the service only if the check below calls for it | Which entry of `X-Forwarded-For` is the visitor's address, for the login throttle. |

Render sets `PORT` itself. `MAKARIOS_DEBUG` defaults to off. The app refuses to start in
production if debug is on, or if the secret key is missing or shorter than 32 characters.
Changing the secret key signs every owner out, which also makes it the emergency logout.

## First-time setup

1. Sign in at render.com with GitHub. Give Render access to this repository only, and add a
   payment method.
2. **New → Blueprint**, choose `zarekcodes/makarios-luxury`, and set the branch (see
   [Which branch](#which-branch)).
3. Render reads `render.yaml` and lists the web service and the database with their monthly cost,
   about $13 in all. Confirm, and the first deploy starts.
4. The site's address is on the service's page, ending in `.onrender.com`.
5. Create the owners' accounts (see [Admin accounts](#admin-accounts)).

## Which branch

During Sprint 5 the Blueprint follows **`sprint-5`**, because the site had to go live within the
sprint, and the sprint's work reaches `main` only when its pull request merges at the sprint
review. Once that pull request merges, switch the Blueprint and the service to **`main`** in their
settings, and leave them there. From then on, production is whatever `main` holds.

## Checking a deploy

```bash
curl -s https://<domain>/api/health                              # {"status":"ok"}
curl -sI -H 'Accept-Encoding: br, gzip' https://<domain>/ | grep -i content-encoding
```

Then load the home page on a phone, and run PageSpeed Insights (mobile) on the URL. The target is
a performance score of 90 or above.

## Rolling back

In the service's **Events** list, find an earlier successful deploy and choose **Rollback**. That
only rolls back the code. A migration that already ran stays applied, which is one more reason
each migration has to stay compatible with the release before it.

## Admin accounts

Each owner has their own account at `/admin`. Accounts are rows in the production database, which
accepts no connections from the internet, so they're managed from the service's **Shell** page in
the Render dashboard:

```bash
python -m app.cli admin-password <name>   # create the account, or set a new password
python -m app.cli admin-remove <name>     # delete it
```

The password is typed at a prompt that doesn't echo, twice, and needs at least 12 characters. A
passphrase of a few words works well. Let each owner type their own password, so nobody else
ever knows it. A new password, or a removed account, signs that owner out everywhere at once.

After five failed logins from one address within 15 minutes, that address is refused until the
oldest failure is 15 minutes old. The count lives in the app's memory, so a redeploy clears it.
Every login, failed login and change made in the admin is written to the service's logs, with
the owner's name.

### Checking the throttle's address

The throttle has to find the visitor's address in `X-Forwarded-For`, where a visitor can write
anything at the start and each proxy adds to the end. After the first deploy, and after any change
in front of the site, send one failed login with a made-up first entry:

```bash
curl -s -o /dev/null -H 'X-Forwarded-For: 10.9.9.9' \
  -d 'username=check&password=check' https://<domain>/admin/login
```

The service's log then shows `admin login failed address=... forwarded=[...]`. `address` must be
your real IP address (`curl -s https://api.ipify.org`), and never `10.9.9.9`. If it's instead an
address belonging to a proxy, raise `MAKARIOS_PROXY_HOPS` by one and check again. Too low only
makes visitors share a count, while too high lets them choose their own address.

## Running the tests against Postgres

CI does this on every push. To do it locally, start a throwaway Postgres in Docker and point the
test suite at it:

```bash
docker run -d --rm --name makarios-pg -p 5433:5432 -e POSTGRES_PASSWORD=test postgres:17
MAKARIOS_TEST_DATABASE_URL=postgresql+psycopg://postgres:test@localhost:5433/postgres uv run pytest
docker stop makarios-pg
```

The suite drops and recreates every table, so never point it at a database with data you want.

## Building the image locally

```bash
docker build -t makarios-luxury .
docker run --rm -p 8000:8000 -e PORT=8000 \
  -e MAKARIOS_DATABASE_URL=postgresql://postgres:test@host.docker.internal:5433/makarios \
  makarios-luxury
```

On Linux, add `--network host` and use `localhost` in the URL instead of `host.docker.internal`.
